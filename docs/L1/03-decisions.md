## Scope cuts (accepted 2026-10-06)

Motivation: the guide grades reasoning, not feature count ("a small, well-justified, well-evaluated system scores higher than a large one that cannot be explained"), and the design had grown to 15–18 containers for one person. **Cuts defer work; the full design stays recorded here and in `02` so it can be restored and the examiner can see what was reserved and why.**

|---|---|---|---|---|---|

| S2 | Tracker + planner | Separate occupancy tracker and evacuation planner | One **responder service**: reads occupancy, computes route, derives status, sends the logged dispatch | Both are slow-path, read-only and share inputs; one job is "tell responders what is happening", and merging removes two containers | Split again if the planner needs independent restart (D11 caching already covers its failure) |
| S3 | ML detector | ML model as main detector (D3, D9 original) | **REVERSED 2026-10-07.** Was: rule-based main, ML stretch (2026-10-06). ## LLM use

**D14 (proposed 2026-10-08, stretch, not built): LLM post-incident reviewer.** An offline batch process reads the audit trail from TimescaleDB (decisions with reasons, commands, dispatches and acknowledgements, dead letters, readings around each incident) and produces (1) a plain-language incident report, (2) patterns across incidents (for example recurring false warnings in one room at lunch), (3) *proposed* configuration changes as validated structured JSON. It never changes the system: every proposal is replayed through the D9 evaluation harness on the same held-out scenarios and seeds, and accepted only if recall holds and false alarms fall, after human approval. Runs on the course GPU server (Gemma, OpenAI-compatible API, plain HTTP client): live control on the edge, slow analysis on external compute. Rejected: letting the LLM set thresholds directly (it cannot measure them; the harness can), and any LLM on the live path. Risks handled: plausible but wrong explanations (checked against data), prompt injection through dead-letter payloads (treated as data, structured output, validation).

**None in v1; the mandatory AI component is the simple learned detector (D3, D9).** The course makes LLM use optional (`project-intro.txt:7`) and notes 4 say the required loop must run without network or model access. An LLM on the safety path would add variability, latency and an injection risk. If one is added, it stays **off the critical path**: for example, drafting the human-readable text of the responder notification from the structured decision record, with allowlisted inputs, validation, a deterministic template as fallback, and no authority to command actuators. The course GPU server offers Gemma 4 over an OpenAI-compatible API (`project-intro.txt:61`), so a plain Go `net/http` client suffices. No LangChain or agent framework is needed. This is a stretch, not a requirement.

## Open items

- ~~**Neighbour-room actuation**~~ **Decided 2026-10-07 (user: heat evidence is fine, but a smoky room next to a fire is not safe to ignore): pre-action behaviour.** Found in the closed-loop run: smoke and CO drifting through an open door put the neighbouring room at fire level on two signals with no heat, and its sprinkler was commanded on (a false actuation, H6). Resolution, modelled on pre-action sprinkler systems (detection arms, a heat-fused head discharges): (1) smoke and CO at fire level without heat **arm** the room (warning: pre-alert to the dashboard and responders, route avoids it) but do not discharge; (2) discharge needs **heat evidence** in that room (temperature at the warning level or rising at the warning rate); (3) **safety valve:** an armed room whose warning persists for `WarnPersist` (120 s) discharges anyway, so a heat sensor that lags, or a smouldering fire, cannot be ignored forever; (4) with the **temperature sensor down** the gate steps aside, so a fire with a failed heat sensor is still caught (D2). Applies to the rule baseline, the model path and the actuator's local fallback. Alternatives not taken: discharge every smoky neighbour (water damage and false actuation, no fire-fighting benefit), or ignore drift (leaves occupants in lethal CO unwarned). Cost, measured: requiring heat removes the model's earlier detection (median delay 110 s with the gate, 80 s for the model alone). Not built: arming neighbours of a room already in `fire` from the door graph (needs adjacency in the detector).
- **Safety floor under the model (D3 amended 2026-10-07):** the rule baseline now floors the learned model: the model can raise the tier but never lower what the rules say (`detector.Deployed`, the Simplex pattern from notes 4). This reverses the earlier "no hard-limit override" residual risk of H1. Reason, measured: the isolation forest rated a room at smoke 5 1/m and CO 500 ppm (flat readings, normal temperature) as **normal**, because the anomaly sat in two of its six features; the rules call it at least a warning. Trade-off: false alarms are the union of both detectors (measured 0.00 on the held-out set), and the model's remaining contribution is smaller than assumed: on these scenarios the deployed classifier detects as fast as the rules alone (110 s). To state honestly in report §11 and §13.
- ~~**Release criterion**~~ **Decided 2026-10-07 (user): keep it conservative.** Smoke and CO decay slowly, so the all-clear (tier none for ClearHold) comes after the room has cooled to ambient, and the sprinkler runs longer than strictly needed (tens of minutes in the closed-loop run). Accepted: extra water is a smaller harm than releasing early on an assumption that the fire is out (D2, safety first). The operator can release earlier (`POST /operator/{level}/{room}/release`, audited). Trade-off to state in the report (§13): water damage and run time. Revisit only if the measured run time turns out to be unreasonable.
